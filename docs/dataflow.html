How to read the claims. Every statement cites the file and line it comes from. Paths starting src/ or examples/ are in this repository; tessera/, canopy/ and cabana/ are the sibling source checkouts the spack environment builds from. confirmed means the behaviour was read in the code. inferred means it follows from code that was read but was not traced end to end, or it depends on behaviour inside a library that was not read. Canopy internals were read at the level of its solve phases and MPI call sites, not line by line.
The defaults do not run today. Solver::requireSupportedConfiguration (src/Beatnik_Solver.hpp:736-879) rejects the default configuration before the first step, and the default --source-quadrature face throws (src/Beatnik_Params.hpp:95, src/Beatnik_FarFieldInterface.hpp:1406-1412). The production path described here is: 
--source-quadrature vertex --no-isotropic-cleanup --remesh-collapse-factor 0 \
--remesh-smooth-iters 0 --remesh-flip-min-gain 1e12
That is: FMM Birkhoff–Rott (--br-approximation fmm is the default, Params.hpp:107), dynamic remeshing every step (split pass only), adaptive dt, and volume preservation on. A frozen-topology run, with no remeshing, adds --no-dynamic-remesh --refine-every 0 (as in scripts/tuolumne/t3_fmm_velocity.flux:128-131).

Overview

The example is a thin driver: main calls MPI_Init, then Kokkos::initialize, parses the command line, and runs Solver::setup(), solve() and finalize() (examples/02_adaptive_mesh_bubble/adaptive_mesh_bubble.cpp:162-224). It instantiates the solver with Kokkos::DefaultExecutionSpace and its memory space (:212-216), which is HIP and HIPSpace on tuolumne. All the work is in the header-only library; the solver uses MPI_COMM_WORLD directly.

Stage 2: timestepping

Solver::solve() loops local_step < steps and breaks early when --t-end is reached (Solver.hpp:337-358). Each iteration calls advanceOneStep() (:417-604):

  1. ++step, then chooseStepSize. With --adaptive-dt, dt = max(dt_min, dt₀·min(1, h_min/h⁰min)^p). h_min is a device parallel_reduce over owned edges followed by Comm::allReduceMin, so every rank gets an identical dt (TimeIntegrator.hpp:228-303). The optional --max-sheet-dt-product clamp adds a halo exchange and two reductions, but it is off by default (Params.hpp:779).
  2. One TVD-RK3 step (TimeIntegrator.hpp:131-174).
  3. allFinite: a device NaN scan, then MPI_Allreduce(LAND). Stopping is collective, so no rank leaves the loop while its peers block (SurfaceState.hpp:568-597; Communication.hpp:309-315).
  4. Dynamic remesh, every --remesh-every steps (default 1), then resetReferenceState, centerPotential, projectToVolume (2 iterations) and another allFinite (Solver.hpp:512-569; VolumeProjection.hpp:219-275).
  5. recordLastFiniteState: a device copy of the four owned arrays, so finalize() can write the last good state (Solver.hpp:906-954).
  6. Checkpoint if due; progress line if due (:599-602).

The integration scheme

Three-stage strong-stability-preserving Runge–Kutta in Shu–Osher form, applied to q = (x, φ) with the same weights for both components (TimeIntegrator.hpp:75-92, 153-173):

q⁽¹⁾  = qⁿ + Δt·L(qⁿ)
q⁽²⁾  = ¾·qⁿ + ¼·q⁽¹⁾ + ¼·Δt·L(q⁽¹⁾)
qⁿ⁺¹ = ⅓·qⁿ + ⅔·q⁽²⁾ + ⅔·Δt·L(q⁽²⁾)

All three stages run through one combine(a₀, a₁, c) kernel, so the stages cannot drift apart. It updates owned rows only; ghosts are refreshed afterwards by finishStage, which does a halo exchange, recomputes the geometry and re-centres φ. Re-centring every stage is required to match the reference, because the next stage differentiates the centred field (:115-129, 310-341).

Stage 3: halo exchanges, and all MPI communication

Beatnik itself issues only MPI_Allreduce, one ring of MPI_Sendrecv (the direct BR solver, not used by default) and MPI_Barrier (I/O). All point-to-point traffic belongs to the libraries:

  • Tessera: mesh halo, mesh edits, halo plans.
  • Cabana: Distributor/migrate in the FMM adapter.
  • Canopy: the FMM's internal exchanges.

3.1 Neighbour discovery

  • No topology communicator. Beatnik and Tessera never call MPI_Comm_dup or MPI_Comm_split, and never build a Cartesian, graph or dist-graph communicator or use neighbourhood collectives. The solver passes MPI_COMM_WORLD through unchanged (adaptive_mesh_bubble.cpp:215-216, Solver.hpp:199-203). confirmed by grep across Beatnik and Tessera. Cabana, however, duplicates the communicator inside every CommunicationPlanBase constructor (cabana/core/src/Cabana_CommunicationPlanBase.hpp:441-458), and the FMM adapter builds up to three of those per evaluation.
  • Peers come from ghost ownership. After distribute, each rank knows every ghost entity as a pair (gid, owning rank), which gives the receive side directly. For the send side, each rank tells every owner which of its entities it ghosts: allToAllV, which is a dense MPI_Alltoall of counts followed by MPI_Alltoallv of gids, on host buffers. The owner maps those gids to local indices, and that list is its send list (tessera/src/Tessera_Distribute.hpp:71-102; tessera/src/Tessera_AllToAllV.hpp:89, 101). confirmed
  • The plan is a custom object, not a Cabana Halo. HaloExchangePlan holds peer lists and offsets as host std::vectors, the send and receive indices as device Kokkos::Views, and two persistent device buffer pools (tessera/src/Tessera_HaloExchange.hpp:53-121). There is one plan per entity kind: vertex, edge and face (Tessera_Distribute.hpp:39-51).
  • When plans are rebuilt. Once at setup. Then inside rebuildHalo at the end of every splitEdges (tessera/src/Tessera_EdgeSplit.hpp:885), so on every remesh step in which any edge splits. The rebuild is coordinator-based and dense: roughly 10–20 allToAllV rounds plus a few Allreduces, then three buildKindPlan calls (tessera/src/Tessera_HaloRebuild.hpp:238-692). inferred The round count was tallied by the trace and not re-counted here.
  • Expected peer count: two (the bands above and below). This holds as long as each band is thicker than the two-ring halo. Very thin bands, at large P on a small mesh, will reach further neighbours. inferred Not measured.

3.2 How a halo exchange is implemented

SurfaceMesh::haloExchange() is one line: Tessera::haloExchange(_mesh, _halo) (MeshInterface.hpp:1348). That function runs three exchanges back to back, one for each entity kind (tessera/src/Tessera_Distribute.hpp:521-528). Each kind runs the same five steps (tessera/src/Tessera_HaloExchange.hpp:134-218) confirmed:

  1. Pack on device. Kernel tessera_halo_pack copies whole AoSoA tuples, out(i) = src.getTuple(send_idx(i)), into a persistent device send buffer, then fences (:156-169).
  2. Post. MPI_Irecv for every receive peer, then MPI_Isend for every send peer. Each message is one contiguous segment of a single registered region per direction, and the MPI datatype is one whole tuple (MPI_Type_contiguous, created and freed on every call) (:171-194, 201).
  3. Wait. MPI_Waitall on the receives, then on the sends (:195-200).
  4. Unpack on device. Kernel tessera_halo_unpack scatters received tuples into the ghost slots, then fences (:204-217).
  5. GPU-aware MPI, no host staging. The buffers are a RegisteredBufferPool<char, MemorySpace>: one grow-only device allocation per direction (1.5× headroom), kept so the Slingshot NIC does not register new memory on every call (tessera/src/Tessera_RegisteredBufferPool.hpp). The device pointers go straight to MPI. That requires MPICH_GPU_SUPPORT_ENABLED=1, which scripts/tuolumne/runtime_env.sh:24 sets. The tuning variables GTL_DREG_CACHE_SIZE and HSA_XNACK are set there too.

3.6 Choices that already reduce message count, size or synchronisation

  • Depth-2 ghosts built once. One exchange per RHS serves the two-ring stencil, instead of two one-ring exchanges per operator (MeshInterface.hpp:136-157).
  • Owner-computes assembly instead of scatter-add. Geometry is assembled from every locally held face, so owned rows come out complete and no reverse halo is needed. Tessera_HaloScatterAdd exists but is never called (MeshInterface.hpp:167-197, 1450-1455).
  • Device-resident halo with registered persistent buffers. Packing stays on the GPU, device pointers go to MPI, and NIC registrations stay bounded (Tessera_RegisteredBufferPool.hpp).
  • Fused reductions. Numerator and denominator travel together in the gauge fixes, the volume projection, the diagnostics and the FMM's 9-word counter block (SurfaceState.hpp:386-388, VolumeProjection.hpp:147-150, FarFieldInterface.hpp:1636-1677).
  • Ghost-consistent updates. centerPotential subtracts the same global constant from ghost rows, so a known-consistent halo stays consistent without a message (SurfaceState.hpp:415-423).
  • Communication-free partition. The partition comes from a deterministic sort of the replicated mesh, with no collective at all.

3.7 Probable missed opportunities

Each item names the evidence. None has been measured; the experiments in §9 are designed to size them.

  1. Redundant halo exchanges. finishStage exchanges, then centerPotential shifts owned and ghost rows alike. The next stage's RHS opens with another haloExchange(), and nothing in between writes mesh data. That makes at least 2 of the 6 exchanges per step look redundant (stages 2 and 3), plus stage 1's when the remesh path has just exchanged. TimeIntegrator.hpp:334-341; ZModelSolver.hpp:207. inferred from reading every write between the two calls.
  2. Whole-tuple exchange of all three entity kinds inside RK. Only vertex x and φ change during a stage: combine writes nothing else, and S is recomputed. Even so, every edge and face tuple is resent six times a step, costing two extra serialized latency rounds per exchange. A vertex-only, two-field exchange would cut roughly two-thirds of the rounds and most of the bytes. Tessera already exposes the vertex plan (MeshInterface.hpp:1401). inferred
  3. No communication/computation overlap. Interior-vertex RHS work does not depend on ghosts and could run between posting and waiting. Nothing is structured that way today (§3.4).
  4. About 16 tiny Allreduces per step, plus remesh diagnostics. The φ̇-mean reduction does not depend on the volume-flux reduction (φ̇ uses the pre-projection normal speed, ZModelSolver.hpp:227-276), so the two could be one 4-word Allreduce. The FMM's 9-word verification reduce runs every evaluation and could be gated behind a debug flag. Remesh diagnostics are about 11 singleton reduces, and auditLongEdges recomputes the entire sizing field, with its halo exchanges and LOR reductions, purely for reporting (DynamicRemesh.hpp:1284-1290).
  5. Three Cabana Distributors per FMM evaluation. Each one dups the communicator, runs Reduce_scatter and barriers, and each migrate barriers again. The code itself names caching the forward distributor as a future optimisation (FarFieldInterface.hpp:1236-1237).
  6. A split forces a full Canopy setup. On the first evaluation after any split, the source count no longer matches, so the routing check fails and Canopy re-runs its whole setup, including ParMETIS (FarFieldInterface.hpp:1474-1495). With --remesh-every 1 that can happen every step.
  7. Dense O(P) collectives on the remesh path. Plan building and split bookkeeping use MPI_Alltoall(v) over all of MPI_COMM_WORLD even though each rank has about two peers. A dist-graph communicator, or a sparse NBX-style exchange, would scale with the neighbour count instead.
  8. A plan rebuild drops the registered pools. halo.vplan = buildKindPlan(…) assigns a fresh plan (tessera/src/Tessera_HaloRebuild.hpp:682-687), contradicting the "pools are retained" intent at Tessera_HaloExchange.hpp:72-73. Every split step therefore reallocates and re-registers halo buffers. confirmed
  9. Static z-band partition, with no load balancing. Refinement concentrates where the sheet rolls up, and those faces stay on their parent's rank. Tessera ships a Zoltan2 loadBalance that Beatnik does not call.

Stage 4: the compute kernel (Birkhoff–Rott) and the FMM

The Birkhoff–Rott integral gives the velocity the vortex sheet induces at every vertex. It is the core kernel: an all-pairs interaction over the whole surface, so it needs far-field evaluation. Here it is treated as a black box. It runs 3 times per step, once per RHS (ZModelSolver.hpp:223-225), and the interface doc calls it "the most expensive collective in the run" (BRSolverBase.hpp:141-146).

  • Selection. createBRSolver switches on --br-approximation. fmm, the default, gives BRSolverFMM; treecode, local and clustered are aliases for it. direct gives BRSolverDirect (CreateBRSolver.hpp:51-77; examples/02_adaptive_mesh_bubble/InputFile.hpp:444-472).
  • Isolation. Only Beatnik_FarFieldInterface.hpp names Canopy types (FarFieldInterface.hpp:18-21; BRSolverFMM.hpp:16).

Data handed to Canopy and what comes back

  • Sources = targets. One source per owned vertex: position x, and a 3-component strength w = A·S, the vertex area times the sheet vector (SourceQuadrature.hpp:225-256). Canopy has no separate target list, which is why only the vertex quadrature is accepted (FarFieldInterface.hpp:549-555, 1406-1412).
  • Particle AoSoA. MemberTypes<Real[3] pos, Real[3] charge, Real[3] output, int[2] tag> in MemorySpace. The tag (origin rank, owned index) is how results find their way home after Canopy permutes and migrates the particles (:788-790, 1194-1219).
  • Control passes into Canopy at these points:
    • Canopy::createSolver on the first call (:899-905, 1421-1427);
    • Solver::auto_maintain on reuse (:919-922, 1472-1473);
    • Solver::setup on the first call or after a split (:911-913, 1492);
    • Solver::solve(particles, compute_gradient = true) (:938-940, 1500).
    Canopy returns gradient(), a View<Real*[3][3]> on device in Canopy's particle order (:948-951).
  • What persists between evaluations. The Canopy::Solver object and two AoSoAs (:1755-1767). Inside Canopy, the tree is rebuilt on every auto_maintain (canopy/src/Canopy_Solver.hpp:493-496). The partition and communication plan are reused only when the cell-key set is unchanged. The M2L operator cache survives until the quantized root box crosses an octave (Params.hpp:440-460). confirmed; the cache detail rests on the comments cited.
  • Parameters.
    • CLI: --br-treecode-theta (MAC θ, default 0.3), --br-treecode-order (expansion order, default 3), --br-treecode-ncrit (leaf size, default 64) (InputFile.hpp:498-515; Params.hpp:194, 229, 256).
    • No CLI option: max_depth 10, replication_depth 3, imbalance_tolerance 0.10, and quantize_root_half_width true.
    • The softening is √blob, which comes from --eps (FarFieldInterface.hpp:1155).

Stage 5: I/O

  • Collective or per-rank. The heavy data is collective parallel HDF5: H5Pset_fapl_mpio (tessera/src/Tessera_HDF5Writer.hpp:187-191) and H5FD_MPIO_COLLECTIVE on every dataset write (tessera/src/Tessera_IoCommon.hpp:235-236). A rank that owns nothing still participates, with an empty selection (:226-232). The /beatnik group, the XDMF files and the symlinks are rank 0 only. The old gather-to-rank-0 path was deleted (IOInterface.hpp:44-56). confirmed
  • Host copy. Cabana::deep_copy of all three AoSoAs, ghosts included, into newly allocated HostSpace AoSoAs on every write (Tessera_HDF5Writer.hpp:115-123). It sits on the critical path of a checkpoint step.
  • Restart is not implemented. CheckpointIO::read and RestartReader::load throw (IOInterface.hpp:780-785; Restart.hpp:178-186).
  • Stdout. Rank 0 prints a progress line at step 1, every steps/10 steps, and every --progress-time-interval (default 0.25). Each one costs a collective Diagnostics::compute (Solver.hpp:1023-1044).
  • Requirement. Checkpoint directories must be on a parallel filesystem. MPI-IO across nodes fails on node-local paths (project CLAUDE.md).

GPU usage

How kernels are expressed

  • Execution and memory spaces. Every Beatnik class is templated on <ExecutionSpace, MemorySpace>. The example instantiates Kokkos::DefaultExecutionSpace and its memory space, which is HIP and HIPSpace on tuolumne (adaptive_mesh_bubble.cpp:212-216).
  • Kernel style. Kernels are flat, labelled Kokkos::parallel_for / parallel_reduce with RangePolicy<ExecutionSpace> over owned or local rows, nearly always followed by Kokkos::fence(). There is no TeamPolicy, MDRangePolicy or execution-space instance on the solver path, so everything runs on the default stream, synchronously. Examples: beatnik_rk3_combine (TimeIntegrator.hpp:318-327), beatnik_far_field_curl (FarFieldInterface.hpp:1513-1525), tessera_halo_pack (tessera/src/Tessera_HaloExchange.hpp:161-168). The direct BR kernel's doc mentions a TeamPolicy, but the code is a RangePolicy with a serial inner loop (BRSolverDirect.hpp:87-88 vs :133-163).
  • Data. Solution fields are not Beatnik Views. They are slots in Tessera's device-resident Cabana::AoSoAs, accessed through slices, so splits, migration and halo exchange carry them automatically (SurfaceState.hpp:51-76). Scratch is Kokkos::View<Real*[3], Device<Exec, Mem>>, allocated once and reused.

Why the split looks like this. The pattern is to keep the arithmetic on the device and keep pointer-chasing, ordered, map-based logic on the host: tree construction, ownership closure, plan building and HDF5. This reading is inferred from where the code puts things. Canopy states it directly: tree construction "runs on host because the tree structure is in _cells… on the host" (canopy/src/Canopy_TreeBuilder.hpp:340-343). The cost of that choice is that every FMM evaluation pays host round trips, because the tree is rebuilt every time.

Ambiguities and open questions

  1. Which configuration counts as "the" run. The example's defaults are rejected at setup (see the warning at the top). This document traces the accepted production configuration: FMM with the vertex quadrature, split-only remeshing every step. Indicator AMR (--no-dynamic-remesh --refine-every N) is a different branch with its own expensive collectives, documented in AdaptiveMesh.hpp but not drawn here. Its 60-probe bisection, when --max-faces binds, reruns the whole closure, halo exchanges included.
  2. Redundant exchanges (§3.7, items 1–2). The reading is that nothing writes the mesh between finishStage and the next RHS. A one-line test would confirm it: compare a run with and without the stage-opening exchange against the gold set.
  3. GPU-awareness of Cabana::migrate is inferred from Cabana packing into device views. The underlying MPI calls were not traced into GTL.
  4. Canopy overlap. Canopy's phases are sequential at solve level. Whether a phase overlaps its own Isend/Irecv with kernels internally was not traced.
  5. MI300A unified memory. HBM is physically shared, but Kokkos still allocates HostSpace and HIPSpace separately, so each "transfer" is a real copy. Whether it goes through the copy engine or runs at memory bandwidth was not measured.
  6. Uncommitted code. device_op_table_assembly (Params.hpp:462-474; FarFieldInterface.hpp:1183) exists only in the working tree on 2026-10-13.
  7. Stale comments. Some Beatnik comments say Tessera lacks edge collapse and flip (MeshInterface.hpp:1563-1625). Tessera_EdgeCollapse.hpp and Tessera_EdgeFlip.hpp now exist, but Beatnik does not call them yet.
